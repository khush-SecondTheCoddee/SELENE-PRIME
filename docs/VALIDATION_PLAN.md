# Validation Plan

**Status:** planned. No tests or benchmarks described here have been implemented or executed.

## Validation rules

- Separate software behavior checks from scientific validation and mission/operational qualification.
- Define expected result, source, tolerance, units, and validity domain before running the implementation.
- Retain inputs, hashes/IDs, software/config versions, actual output, absolute/relative errors (when defined), status, environment, and execution date.
- Record unavailable references as pending. Do not infer pass from import success, self-consistency, or matching an output generated by the same algorithm.
- Use deterministic synthetic fixtures for controlled geometry; label results synthetic, not real lunar-data validation.
- Compare successive refinements and independent references. Highest resolution is not ground truth by default.

| Layer | Cases | Evidence / pass rule |

| Convergence | Refine disk quadrature, azimuth/range terrain sampling, ray sampling, genuine nested DEM resolutions where available, uncertainty sample count | Tabulate successive differences and reference error; show stable trend or report non-convergence. |
| End-to-end reproducibility | Repeat pinned benchmark configuration | Compare output/schema within declared platform tolerance; verify hashes and provenance; record stochastic seed. |

## Required analytic and synthetic cases

1. Solar disk entirely visible, entirely occulted, and centered on a straight horizon. Limits are 1 and 0 within floating-point tolerance; a half-plane case is symmetric under uniform-disk assumptions.
2. Two apparent circular disks with no overlap, containment, tangency, and partial overlap, checked against independently derived circle-overlap area.
3. Flat terrain under selected lunar curvature; isolated ridge with specified geometry; symmetric valley; isolated peak; multiple ridges; antimeridian crossing; NoData boundary.
4. DEM interpolation values from independently calculated bilinear cases, including centers/edges, wrap, and NoData neighborhoods.
5. Frame transforms checked against separate authoritative SPICE invocation and rotation invariants; missing-frame-kernel failures.
6. Coordinates checked against independent equations and source-backed reference points for the selected datum.
7. Genuine PDS/LOLA sample product inspected against label, dimensions, encoding, units, scaling, and checksum source.
8. Solar irradiance compared with identified reference/passband, stating uncertainty and geometry normalization.

## Benchmark record format

Each row includes case ID/category; synthetic/real designation; source/version; input identifiers/hashes; epoch/frame/datum/units; algorithm/configuration; expected value; tolerance and justification; actual value; absolute error; relative error if defined; status (`pass`, `fail`, `pending`, `not-applicable`); execution environment/date; notes and limitations.

## Numerical tolerance policy

No numerical tolerances are selected in Phase 1. For each case, allocate error across reference uncertainty, input uncertainty, discretization, interpolation, and implementation. Tolerance must not be tuned after results merely to obtain a pass. If reference uncertainty exceeds the requirement, classify the case as inconclusive and improve the reference or narrow the claim.

## Release evidence gates

- **G1 — Design:** supported data/frame/passband/use cases and error budgets selected with sources and limitations.
- **G2 — Unit foundation:** core primitives and invalid-input behavior covered; no scientific module self-validates solely through itself.
- **G3 — Real-data integration:** at least one genuine, identified terrain product and compatible genuine kernel set query successfully at stated epochs; provenance survives end to end.
- **G4 — Independent validation:** required analytic and external/reference cases executed and reported, with failures/pending cases visible.
- **G5 — Convergence/uncertainty:** successive refinements and uncertainty studies executed with separate error categories.
- **G6 — Audit:** independent red-team review completed; critical/high findings resolved or research-evaluation readiness withheld.

Passing G1–G6 supports only documented use cases. It does not imply NASA approval, flight qualification, or mission readiness.
