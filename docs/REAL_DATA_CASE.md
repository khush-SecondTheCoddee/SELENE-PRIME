# Reproducible real-data case

The Apollo 11 demonstration is run with `python scripts/run_apollo11_case.py` from the repository root after installing the `spice` extra. It requires local input files under `data/real/` and the individually hash-pinned manifest `config/research_kernels_de421.json`. The raw files are intentionally excluded from Git; see `docs/REPRODUCIBILITY.md` and `docs/TERRAIN_DATA.md` for acquisition sources.

The case uses NASA's published Apollo 11 coordinate (0.67409° N, 23.47298° E), the PDS3 LOLA `LDEM_16` cylindrical GDR (16 pixels per degree), DE421, and 2024-04-08 18:00:00 UTC. The coordinate is listed by the [NASA Apollo 11 Mission Overview](https://www.nasa.gov/wp-content/uploads/static/history/alsj/a11/a11ov.html). The LOLA archive convention and ME frame are specified in the [LOLA RDR SIS](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/document/rdrsis.htm), and NAIF documents the DE421 frame definitions and compatibility in [moon_080317.tf](https://naif.jpl.nasa.gov/pub/naif/generic_kernels/fk/satellites/moon_080317.tf). Coordinates are transformed from `IAU_MOON` to the product's `MOON_ME_DE421` frame at the observation epoch before sampling the DEM. The DEM's planetocentric latitude, east-positive longitude, pixel-center registration, and 1,737,400 m reference sphere are retained from the product label.

The script writes `reports/real_case/apollo11_2024-04-08T180000Z.json`, including source hashes, loaded-kernel provenance, state-query evidence, apparent geometry, horizon sampling refinements, numerical disk quadrature, a separate analytical circle-overlap calculation, and a deterministic subpixel site-location sensitivity experiment. The second LOLA-host file is byte-for-byte compared with the archive copy; it is not represented as an archive-published cryptographic checksum.

## Calibration and interpretation

Calibration means comparison against separate calculation paths for the specified outputs. The apparent-position comparator solves the light-time root with bisection over direct SPICE geometric states while the product service uses fixed-point iteration. This tests the solver implementation, but both paths use DE421, so it does not independently validate the ephemeris. The interpolation comparator directly evaluates the four source samples. The circle-overlap comparator is an analytical planar geometry solution; for small angular disks this is a useful validation, with its tangent-plane approximation explicitly retained.

The convergence report compares successively refined terrain ray steps and solar disk grids. These are numerical error indicators, not a claim that the finest grid is truth. Site jitter within half a DEM pixel measures sensitivity to where the published site lies relative to this raster; it is not a probability distribution for site error. The PDS label does not provide a formal vertical uncertainty. A uniform solar disk (zero limb-darkening coefficient) and an opaque airless Earth are used for the geometric case. The irradiance scale is the IAU nominal bolometric 1361 W/m² at 1 AU, whose commonly cited measurement basis is SORCE/TIM; this run does not propagate solar-cycle or input uncertainty and is not a passband-specific radiometric calibration. See [NASA GSFC solar irradiance science](https://earth.gsfc.nasa.gov/climate/projects/solar-irradiance/science) and [LASP TIM science](https://lasp.colorado.edu/tsis/instruments/tim-total-irradiance-monitor/tim-science/).

A sub-1% claim applies only if the JSON provides a defined non-degenerate metric and the comparison is sufficiently independent for that claim. A zero-visibility case is assessed with absolute visible-fraction error, not relative error. The report does not imply NASA approval, CLPS qualification, mission readiness, or a contest result.
